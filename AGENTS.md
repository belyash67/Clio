# AGENTS.md — правила работы AI-агента над Clio

## Контекст

Clio — реальная социальная PWA-платформа для любителей кино, сериалов и анимации. Владелец не обязан быть профессиональным разработчиком. Прочитай `README.md` полностью перед любой архитектурной работой и перед крупными изменениями. README — источник продуктовых требований и зафиксированных решений; этот файл — правила выполнения задач.

## Обязательные ограничения

1. **Бюджет 0 ₽:** не подключай платные услуги, тарифы, пробные периоды с автосписанием и ресурсы, требующие карты. Не выполняй никаких платных действий без явного согласия владельца.
2. **Россия без VPN:** публичная версия должна быть доступна друзьям из РФ, включая критичные внешние ресурсы. Не утверждай, что доступность проверена, без реального теста из РФ.
3. **Настоящая реализация:** не выдавай заглушки, фиктивные API, захардкоженные пользовательские данные и декоративные кнопки за готовую функциональность. Временные моки допустимы только в изолированных тестах или явно обозначенных прототипах с разрешения владельца.
4. **Не торопись:** сначала архитектура, ER-диаграмма и план; затем маленькие законченные этапы. Не начинай следующий крупный этап без проверки предыдущего и согласия владельца.
5. **Безопасность:** серверные проверки прав, валидация, защита сессий и секретов обязательны. Не позволяй пользователю назначить себе admin или изменять чужие данные.
6. **Переносимость:** стандартный PostgreSQL и переменные окружения. Не привязывай бизнес-логику к конкретному провайдеру.
7. **Не принимай спорные продуктовые решения молча:** см. «Открытые вопросы» в README. Задавай владельцу короткие конкретные вопросы.

## Технологический ориентир

- Next.js + React + TypeScript + Tailwind CSS + Lucide.
- Next.js Server Actions / Route Handlers для серверной логики.
- PostgreSQL + Drizzle ORM (окончательно подтвердить до установки).
- Better Auth или обоснованная альтернатива с PostgreSQL.
- TMDB API на сервере с кэшем, дедупликацией и соблюдением лицензии.
- PWA для iOS, Android, Windows, macOS.
- Git + GitHub для истории версий.

Если предлагаешь замену технологии, объясни простыми словами преимущества, недостатки, стоимость и влияние на доступность в РФ. Не меняй стек без согласования.

## Рабочий процесс

1. Сначала изучи структуру репозитория, `README.md`, этот файл и существующие изменения Git.
2. Кратко изложи понимание задачи, затронутые файлы, риски и критерии готовности.
3. Если задача неоднозначна, спроси владельца, не придумывай требования.
4. Перед правками предложи небольшой план. Для крупных или разрушительных действий обязательно получи подтверждение.
5. Вноси минимальные логически завершённые изменения, не переписывай несвязанный код.
6. После изменений запусти доступные проверки (lint, typecheck, tests, build по необходимости), сообщи фактические результаты. Если запуск невозможен, объясни почему; не заявляй, что всё протестировано.
7. Покажи список изменённых файлов, что сделано, что осталось и как владельцу проверить результат.
8. Обновляй документацию и миграции вместе с кодом.
9. Предлагай понятное сообщение коммита; не делай push, merge, release или deployment без явного разрешения.
10. Не удаляй и не перезаписывай пользовательские изменения, не выполняй `git reset --hard`, `git clean -fd`, удаление БД или разрушительные миграции без отдельного подтверждения.

## Стандарты реализации

- TypeScript со строгой типизацией; читаемые имена, небольшие модули, минимум ненужных зависимостей.
- Валидация входных данных и проверки владения ресурсами на сервере.
- Параметризованные SQL-запросы, миграции, PK/FK, уникальные ограничения, индексы.
- Секреты только в `.env`/окружении сервера, `.env.example` без реальных секретов; секреты не должны попадать в Git, логи или браузерный bundle.
- Изображения не хранить бинарно в PostgreSQL.
- Для TMDB уникальность `(tmdb_media_type, tmdb_id)` и серверное кэширование; не путать ID фильмов и сериалов.
- Учитывать приватность при формировании ленты, поиске пользователей и публичных профилях.
- Пагинация, загрузочные и пустые состояния, обработка ошибок, доступность интерфейса.
- Адаптивность: мобильная нижняя навигация, десктопная боковая панель; тёмная тема по умолчанию, светлая и системная.
- Не внедрять платные SDK, облачные сервисы или аналитику без отдельного согласования.

## Git и управление версиями

- Проверяй `git status` перед работой; сохраняй незакоммиченные изменения владельца.
- Работай небольшими задачами; не смешивай рефакторинг и новые функции без причины.
- Коммиты должны быть понятными, например `feat(catalog): add TMDB search`.
- Для рискованных изменений предлагай отдельную ветку.
- Не публикуй репозиторий и не меняй настройки приватности без разрешения.

## Формат общения

- Пиши по-русски, коротко и понятно, без лишнего жаргона.
- Объясняй владельцу, какие действия нужно выполнить в VS Code, терминале, GitHub или панели хостинга.
- Если есть варианты, рекомендуй один с кратким обоснованием.
- Различай: **реализовано**, **запланировано**, **требует проверки**.
- Не обещай бесплатность, доступность в России, безопасность или работоспособность без проверки.

## Первая задача после прочтения файлов

**Не создавай приложение и не устанавливай зависимости автоматически.** Сначала:

1. Проверь текущую структуру проекта и состояние Git.
2. Составь компактную архитектуру MVP с учётом 0 ₽ и доступа из РФ.
3. Предложи схему БД и ER-диаграмму на обсуждение.
4. Укажи решения, которые надо согласовать до кода.
5. Дождись разрешения владельца на реализацию первого этапа.
