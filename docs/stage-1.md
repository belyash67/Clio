# План первого этапа разработки

Статус: владелец подтвердил рабочий вход после настоящего письма подтверждения и разрешил продолжить разработку каталога. PostgreSQL и Gmail подключены. Регистрация, подтверждение, вход и сброс пароля проверены интеграционными тестами; сценарий восстановления с настоящим письмом, проверки двух пользователей и перенос всех строк в словари остаются в списке до публичного запуска.

## Текущее состояние

- Созданы Next.js/React/TypeScript/Tailwind, формы аккаунтов, профиль, смена пароля и завершение остальных сессий, переключение темы.
- Созданы Drizzle-схема и первая SQL-миграция: users, sessions, accounts, verifications, rate_limits, user_settings, user_roles.
- Серверные операции профиля используют ID из сессии; входные поля проверяются строгой схемой. Тесты входной валидации не доказывают полную безопасность авторизации.
- При отсутствии конфигурации формы недоступны, auth API отвечает 503. Без сессии /profile перенаправляет на /login.
- Локально прошли lint, typecheck, три теста и production build; страницы проверены HTTP-запросами. Визуальная проверка в браузере и интеграционные проверки с БД ещё не выполнены.
- Проверены локальная PostgreSQL, создание отдельного пользователя clio без административных прав, применение миграции и наличие семи таблиц. Пароль postgres после настройки удалён из .env.local.
- Исправлена ошибка регистрации: для rate_limits.id добавлен SQL DEFAULT gen_random_uuid()::text отдельной миграцией. Регрессионный тест на настоящем PostgreSQL воспроизвёл ошибку до исправления и прошёл после; тестовые изменения откатываются. HTTP-запрос регистрации без полей возвращает 400 VALIDATION_ERROR вместо 500.
- Режим Better Auth generateId: uuid требует генерации UUID на стороне БД и для users, accounts, sessions, verifications. Для них применена миграция 0002_conscious_husk.sql; предыдущая проверка счётчика не покрывала создание аккаунта.
- Добавлен полный auth-тест в отдельной случайной PostgreSQL-схеме: регистрация, запрет входа без подтверждения, подтверждение email, вход и сессия, запрос сброса, смена пароля, отзыв старой сессии, отказ старого пароля и повторного использования токена. Исходная ошибка воспроизведена до исправления; после исправления два интеграционных теста прошли. Почта перехватывается только в этом изолированном тесте; доставка через настоящий Gmail ещё требует проверки владельцем.
- Добавлена команда npm.cmd run test:db для регрессионного теста БД. Четыре обычных теста, lint и typecheck прошли после исправления. Ошибки сервера и неподтверждённого email теперь различаются в интерфейсе.
- Не завершены: проверка реальной доставки и восстановления, проверки двух пользователей, перенос всех строк в словари и остальные интеграционные тесты.
- npm audit выявил 11 moderate-предупреждений в цепочках drizzle-kit/esbuild и ESLint/minimatch. Даже audit --omit=dev показывает четыре предупреждения: drizzle-kit попадает в дерево через optional peer Better Auth. Совместимый audit fix их не устранил. Принудительный downgrade и неподтверждённые overrides не применялись. Это остаётся техническим долгом; перед публикацией выполнить повторную проверку и проверить состав production-артефакта.

Инструкция владельцу: [локальный запуск и настройка](local-setup.md).

### Подтверждение email

- После регистрации email сохраняется как подсказка в sessionStorage текущей вкладки; он не попадает в URL. Страница /verify показывает адрес и кнопку повторной отправки без повторного ввода. При отсутствии подсказки остаётся форма ввода, при успешном входе подсказка очищается.
- Повторная отправка имеет 60-секундную паузу в интерфейсе и серверные ограничения частоты. Ошибка почтовой отправки больше не предлагает менять пароль или создавать аккаунт заново.
- Найден тайм-аут DNS Gmail у dev-сервера, запущенного в ограниченной среде агента. Сервер перезапущен с сетевым разрешением. Настройки DNS и проверка TLS не ослаблялись.
- Настоящий запрос повторной отправки подтверждения существующему аккаунту владельца вернул 200 после успешной отправки через SMTP. Фактическое появление письма во входящих и переход по ссылке должен подтвердить владелец.
- После изменений прошли lint, typecheck, 6 обычных и 2 интеграционных теста, включая повторную отправку в изолированной схеме. Визуальная проверка новой формы не выполнена: browser access host недоступен.

## Цель

Подготовить техническую основу и получить первый настоящий сценарий: зарегистрироваться, подтвердить email, войти, открыть собственный профиль и выйти. Это внутренний этап, не готовый публичный релиз Clio.

## Последовательность

1. Проверить установленное окружение и выбрать совместимые стабильные версии. Ничего не скачивать без разрешения на реализацию.
2. Инициализировать Next.js, строгий TypeScript, Tailwind и Lucide. Добавить lint, typecheck, тестовый инструмент, .gitignore и .env.example без секретов.
3. Подключить локальный PostgreSQL через DATABASE_URL, Drizzle и миграции. Если PostgreSQL отсутствует, отдельно объяснить способ установки; не устанавливать автоматически системное ПО.
4. Подключить Better Auth и добавить профиль, настройки, роли. Не писать собственное хеширование паролей и управление токенами.
5. Реализовать регистрацию с username/email/паролем, подтверждение email, вход/выход, восстановление доступа и отзыв сессий. До подключения настоящей почты считать email-сценарий незавершённым; не обозначать вывод ссылки в консоль как доставленное письмо.
6. Добавить редактирование собственного имени и био, закрытые настройки приватности, темы и основу локализации. Интерфейс только для реальных действий; будущие разделы не изображать работающими.
7. Проверить ограничения доступа, повторные запросы, истёкшие токены, ошибки БД и перезапуск приложения. Показать владельцу результат и актуальный список ограничений.

## Проверки готовности

- lint, typecheck, значимые тесты и production build проходят; сообщаются реальные команды и результаты.
- Миграции применяются к чистой локальной БД; данные сохраняются после перезапуска.
- Username и email не дублируются независимо от регистра; слабые/невалидные входные данные отклоняются.
- Подтверждение и сброс пароля работают через настоящий согласованный почтовый канал; повторное и просроченное использование токенов отклоняется.
- Пользователь A не может изменить профиль или настройки B, назначить себе admin или получить чужую сессию.
- После выхода и отзыва сессии закрытые операции недоступны; закрытые поля не попадают в публичные ответы.
- Проверены мобильная и десктопная компоновки, клавиатура, ошибки, пустые и загрузочные состояния.
- Секреты отсутствуют в Git и клиентских ответах.

Без настоящей доставки писем этап может быть показан как частично готовый, но не принят как завершённый. Проверка из РФ и публичный PWA относятся к подготовке запуска, не подменяются локальными тестами.

## Правила перехода

Завершать этап демонстрацией и проверками, следующий крупный этап начинать после согласия владельца. Никаких push, merge, deployment или платных действий без явного разрешения. Технические решения внутри согласованного этапа агент принимает самостоятельно; к владельцу обращается по конкретным препятствиям и новым продуктовым вопросам.
